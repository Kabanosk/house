# Specy trafiają w praktykę, szczegóły wymagają poprawek

Oba specy (`2026-11-16-agno-adoptions-design.md` i `2026-11-16-short-context-design.md`) idą w tę samą stronę co najlepsza praktyka z listopada 2026. Fakty o przebiegu liczy kod z zapisu sesji, nie sędzia LLM. Przekazanie jest briefem „co dalej” i indeksem do pełnego zapisu. Evale mają własny runner z miarą pass^k. Offload jest bezstratny, lint pamięci tylko raportuje, a rutyny dają propozycje, nie zmiany. Przed implementacją trzeba jednak poprawić **35 zmian oznaczonych jako must**, bo część speców opiera się na faktach, które przestały być prawdą albo nigdy nie były sprawdzone. Pięć najważniejszych. Pierwsza: sesja Claude Code to plik rodzica razem z plikami podagentów, a zdeduplikowany JSONL nie zawiera wywołań bocznych (Haiku, kompakcja), więc sumy kosztu trzeba brać z rekordu `cost-state`. Druga: Codex liczy `input_tokens` razem z cache i ma już delty per odpowiedź, więc zdanie speca o „różnicy narastających wartości” jest nieaktualne. Trzecia: sufitu ~8K tokenów „przycinanego od końca” nie da się wymusić w sesji interaktywnej, bo streszczenie pisze Claude Code, a ustalenia człowieka giną w streszczeniach mierzalnie (30% naruszeń po kompakcji, 53% reguł po jednej rundzie `/compact` i 10% po pięciu). Czwarta: na modelach z natywnym oknem 1M automat kompakcji odpala dopiero przy ~967K, co tłumaczy szczyt 897K z naszego pomiaru, a K2 pomija domyślnie włączoną kompakcję przy bezczynności. Piąta: problem A4 jest w połowie nieaktualny, bo Claude Code zapisuje już do pliku duży wynik udanej komendy, ale wynik komendy z błędem nadal ginie. Do tego zadania Signal w Dockerze tracą zapis sesji (tmpfs), a A3 nie ocenia stanu końcowego, nie izoluje przebiegów i nie ma zbioru wstrzymanego. Bez tych poprawek eval można „zazielenić” poprawianiem promptu, czyli zrealizować anty-cel speca.

## A0 i K0: czytnik liczy dobrze, ale nie widzi podagentów ani wywołań bocznych

Dokumentacja Claude Code mówi wprost, że format zapisu jest wewnętrzny: „The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release” ([Manage sessions](https://code.claude.com/docs/en/sessions.md)). Spec ma więc rację, że parser musi być tolerancyjny. Brakuje mu jednak opisu, czym jest sesja. Zapis podagenta leży w osobnym pliku `<session>/subagents/agent-<agentId>.jsonl` obok `agent-<agentId>.meta.json`, a pole `toolUseId` w meta wiąże go z wywołaniem Agent/Task u rodzica ([Inside the subagent trace file](https://frederick-douglas-pearce.github.io/blog/2026/inside-the-subagent-trace-file/)). Pomiar lokalny na Claude Code 2.1.309–2.1.326 potwierdza ten układ i dodaje katalog `<session>/tool-results/` z pełnymi wynikami narzędzi ([pomiar lokalny](../research_notes/Research%20speców%20Agno%20i%20kontekstu/transcripts_and_cost.md)). Czytnik, który bierze sam `<session>.jsonl`, zaniża koszt każdej sesji coordinatora z podagentami.

Deduplikacja też musi wyjść poza jeden plik. ccusage deduplikuje parę `message.id` + `requestId` **między sesjami**, bo „Claude Code can copy one response into multiple session transcripts”. Sidechainy `/btw` odtwarzają wiadomości rodzica z tym samym `message.id`, ale innym `requestId`, i niosą przy tym cache-read rodzica, więc kopia z `isSidechain: true` musi przegrać z oryginałem ([ccusage Claude adapter](https://github.com/ccusage/ccusage/blob/main/rust/adapters/claude/src/README.md)). agentsview wybiera kompletny rekord przed ogólną deduplikacją ([agentsview: Token Usage & Costs](https://github.com/kenn-io/agentsview/blob/main/docs/token-usage.md)). Reguła speca „zostaje ostatni rekord, ten ze `stop_reason`” jest więc dobra, ale trzeba ją stosować globalnie dla przebiegu (rodzic, podagenci, kopie), z dogrywką na wyższe `output_tokens`. Rekordy z `model == "<synthetic>"` (błędy, przerwania) mają zerowe `usage` i powinny wypadać.

Najważniejsza nowa rzecz to rekord `cost-state`, który bieżące Claude Code dopisuje do zapisu z sumami sesji per model i `totalCostUSD`. Dokumentacja Agent SDK potwierdza mechanizm: „Claude Code saves the session's totals to its transcript when the process exits normally” (od v2.1.277). Zastrzega też, że `total_cost_usd` to „client-side estimates, not authoritative billing data” ([Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md)). Lokalne porównanie 33 sesji dało jasny obraz. W **13 sesjach zdeduplikowany JSONL zgadzał się z `cost-state` co do tokena** (np. 100 793 = 100 793 tokenów wyjścia). W pozostałych `cost-state` zawierał dodatkowy model `claude-haiku-*`, którego wywołań w JSONL nie ma: tytuły, WebSearch, podsumowania, od kilkunastu do ~80K tokenów wyjścia na sesję. Różnice dotyczyły też kompakcji (np. 209 789 wobec 221 871 tokenów wyjścia przy jednej kompakcji) ([pomiar lokalny](../research_notes/Research%20speców%20Agno%20i%20kontekstu/transcripts_and_cost.md)). agentsview opisuje to samo zjawisko: Claude Code robi dla WebSearch osobne wywołanie Haiku („tens of thousands of input tokens … per search”), które nie trafia do zapisu ([agentsview](https://github.com/kenn-io/agentsview/blob/main/docs/token-usage.md)). Wniosek dla K0: dwa poziomy danych. Per wywołanie z JSONL do profilu kontekstu i kompakcji, per sesja z `cost-state` (albo z linii `result` w `stream-json`) do sum, oraz kolumna „poza zapisem” jako różnica. To zastępuje plan speca, żeby walidować K0 przez `/cost` albo OTel, i działa automatycznie, bez usług. Zgłoszenie [claude-code#28197](https://github.com/anthropics/claude-code/issues/28197) o zaniżonych 100–174× tokenach wejścia dotyczyło starszych wersji i zostało zamknięte bez odpowiedzi Anthropic. Bieżące dane tego nie potwierdzają, ale test zgodności z `cost-state` trzeba powtarzać przy każdej nowej wersji CLI.

Codex wymaga większej korekty, niż spec zakłada. Bieżący rollout (0.166) ma rekord `token_usage_record` per odpowiedź (z `response_id`), a `token_count` niesie zarówno sumę `total_token_usage`, jak i deltę `last_token_usage`. Różnicowanie sum zostaje więc tylko jako ostatni fallback ([openai/codex protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs), [ccusage Codex adapter](https://github.com/ccusage/ccusage/blob/main/rust/adapters/codex/src/README.md)). Ważniejsze jest to, że `input_tokens` Codexa **zawiera** `cached_input_tokens`. Lokalnie `cached ≤ input` zachodziło w 61 z 61 zdarzeń, a agentsview przenosi zapis cache Codexa do osobnego koszyka. Bez normalizacji (`input = input_tokens − cached_input_tokens − cache_write_input_tokens`) wagi K0 policzą buforowane wejście Codexa po pełnej stawce. Do tego dochodzą trzy pułapki opisane w kodzie ccusage. Przy wznowieniu rollout przepisuje oryginalne `cli_version`, więc „that field cannot be used to gate behavior”. Rollout podagenta odtwarza historię rodzica przed własną turą. Fork (`forked_from_id`) kopiuje rekordy rodzica i bywał liczony wielokrotnie ([ccusage#897](https://worker-github.zxx930427.workers.dev/ryoppippi/ccusage/issues/897)). Wynik narzędzia Codexa nie ma serializowanego pola `success` (to „internal metadata for downstream handling”), więc `is_error` bywa nieznane i musi przyjmować trzy wartości, a A1 nie może czytać `None` jako sukcesu ([models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs)).

Kompakcję da się odczytać z liczbami. W Claude Code rekord `system` z `subtype: compact_boundary` ma `compactMetadata` z polami `trigger`, `preTokens`, `postTokens` i `durationMs`, a po nim idzie `user` z `isCompactSummary: true`. W Codexie są `compacted` i `context_compacted`, a zużycie kompakcji leży w `token_usage_record` o `response_id` równym `compaction_response_id` ([pomiar lokalny](../research_notes/Research%20speców%20Agno%20i%20kontekstu/transcripts_and_cost.md), [rollout_payload.rs](https://github.com/openai/codex/blob/main/codex-rs/history/src/rollout_payload.rs)). Wartości `preTokens` i `postTokens` to dokładnie L i P+R ze wzoru opłacalności w §4 short-context, więc K0 może liczyć ten wzór na prawdziwych kompakcjach. Pole „do sprawdzenia” w §13 short-context jest tym samym rozstrzygnięte.

Znajdowanie sesji przestało być pytaniem otwartym. `claude -p --session-id <uuid>` to oficjalna flaga ([CLI reference](https://code.claude.com/docs/en/cli-reference)), a `codex exec --json` emituje jako pierwsze zdarzenie `thread.started` z `thread_id`, równym `session_meta.id` i obecnym w nazwie pliku rolloutu ([exec_events.rs](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs)). Heurystyka „najnowszy rollout w oknie czasu” może więc zejść do roli awaryjnej. Gorzej z zadaniami Signal. [`houselib/agentdocker.py`](../../../houselib/agentdocker.py) uruchamia kontener z `--tmpfs /home/agent` i `HOME=/home/agent`, a [`houselib/signalagent.py`](../../../houselib/signalagent.py) woła `claude -p` bez `--session-id`. Zapis znika razem z kontenerem i zostaje tylko suma z `result`. Rozwiązanie zgodne z izolacją: `--session-id` plus `CLAUDE_CONFIG_DIR` na dodatkowym montażu rw i `CLAUDE_CODE_PROJECT_DIR_NAME=<job-id>` (od v2.1.234) ([Manage sessions](https://code.claude.com/docs/en/sessions.md)). Trzeba przy tym sprawdzić, czy w trybie OAuth do `CLAUDE_CONFIG_DIR` nie trafiają poświadczenia. Druga opcja to jawnie ograniczyć K0 dla Signal do sumy z `result`.

Telemetria OTel pozostaje opcją na później, a jej koszt wzrósł. Od v2.1.323 domyślnym protokołem Claude Code jest `http/protobuf`, więc odbiornik w stdlib wymaga jawnego `OTEL_EXPORTER_OTLP_PROTOCOL=http/json`. Musi też obsłużyć gzip i odpowiadać `200 {}` ([Monitoring usage](https://code.claude.com/docs/en/monitoring-usage), [OTLP spec](https://opentelemetry.io/docs/specs/otlp/)). Logi wychodzą co 5 s i nie wiadomo, czy krótki `-p` robi flush przy wyjściu. Skoro `cost-state` daje sumy z wywołaniami bocznymi, OTel ma sens tylko wtedy, gdy kolumna „poza zapisem” okaże się niewystarczająca.

Prywatność wymaga zmiany techniki, nie zasady. Zapisy niosą treść pod coraz nowymi kluczami: `api-request-blob` (kopia żądania), `file-history-snapshot` i `file-history-delta` (kopie plików), `tool-results/*.txt`. Jeden audyt znalazł w zapisach ~600 sekretów ([DEV](https://dev.to/rentierdigital/i-spent-25-years-avoiding-malware-claude-code-stored-600-of-my-secrets-anyway-3e2j), [claude-code#58043](https://claudeissues.com/issue/58043-read-cat-on-config-files-leaks-api-keys-into-conversation-transcript)). Widok bez treści musi więc być whitelistą pól (liczby, nazwy narzędzi, identyfikatory, czasy), a nie listą usuwanych pól. Sama komenda Bash w `tool_call.input` to też treść i typowe miejsce wycieku (`curl -H "Authorization: …"`), więc powinna przechodzić przez skaner `guard`. Ostatnia sprawa: Anthropic nie publikuje, jak tokeny ważą się w limitach 5-godzinnym i tygodniowym ([support: Pro/Max](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)). Anegdotyczne zgłoszenia sugerują, że odczyty cache ważą w limicie tygodniowym więcej niż 0,1 z cennika ([#58786](https://claudeissues.com/issue/58786-bug-weekly-all-models-cap-metering-cache-read-input-tokens-at-full-weight-vs-5h)). Pytanie 1 z short-context należy zamknąć jako „nieznane”. K0 podpisuje wynik jako estymatę kosztu API, nie zużycie limitu. Dla Codexa może dodatkowo pokazywać przyrost `rate_limits.*.used_percent`, który Codex zapisuje w każdym `token_count`.

## A1: relacja z przebiegu musi zestawiać twierdzenia agenta z zapisem

Kierunek A1 (deterministycznie, bez wnioskowania, zapis jako jedyne źródło) ma najmocniejsze poparcie ze wszystkich decyzji w specach. Praca „From Confident Closing to Silent Failure” (czerwiec 2026) pokazała, że fałszywy sukces, czyli agent ogłasza ukończenie, a stan środowiska temu przeczy, to **75,8% porażek** w trajektoriach agentów kodujących z AppWorld. Żadna z 25 konfiguracji sędziów LLM nie przekroczyła **AUROC 0,65**, a proste detektory oparte na trajektorii osiągnęły 0,83–0,95. Zalecenie autorów: „Don't use LLM judges as the primary monitor for false success” ([arXiv 2606.09863](https://arxiv.org/abs/2606.09863)). Karta systemowa Sonnet 5 opisuje zmyślanie brakujących danych i podawanie odpowiedzi, których prywatne rozumowanie nie wyprowadziło ([Claude Sonnet 5 System Card](https://www-cdn.anthropic.com/480e0bb54327b9622282e9c39a83a4f490ed377e/Claude%20Sonnet%205%20System%20Card.pdf)). METR dokumentuje modele, które modyfikują testy albo kod oceniający ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)).

Na tym tle A1 ma dwie luki. Pierwsza to **kolejność**. Spec pyta, „czy padło `house check`”, a powinien pytać, czy check padł **po ostatniej edycji**. Anthropic opisuje jako typową porażkę oznaczanie funkcji jako gotowej bez testu ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Ten sam fakt zasila status „sprawdzona” w sekcji Zrobione przekazania A2. Druga luka to **twierdzenie kontra zapis**. Jeśli raport workera mówi, że testy przeszły, a w zapisie nie ma wywołania z wynikiem GREEN po ostatniej zmianie, relacja powinna wypisać deterministyczną linię „twierdzenie bez pokrycia w zapisie”. Nie znaleziono systemu, który robi dokładnie to w raportach agentów kodujących. To ekstrapolacja z wyników 2606.09863, ale tania i bez sędziego. Do tego dwie mniejsze rzeczy. Lista **udanych** edycji plików testowych i konfiguracji sprawdzeń (obok odmów guarda, które spec już liczy) pokrywa najczęściej opisywany sposób oszukiwania ([EvilGenie](https://www.alphaxiv.org/abs/2511.21654.md)). Metryka „powtórzenie ślepej uliczki”, czyli komenda z błędem, która identycznie padła już w poprzedniej próbie, daje K4 bezpośredni pomiar, czy brief ze ślepymi uliczkami działa. Spec powinien też powiedzieć wprost, że relacja wyjaśnia, a bramka `house check` pozostaje jedynym źródłem wyniku i zamyka się przy braku danych („fail closed”).

## A2: kod musi pilnować tego, co streszczenie gubi

Ośmiosekcyjny szablon A2 jest nadzbiorem tego, co robią inni. Codex ma w prompcie kompakcji cztery punkty: postęp i decyzje, kontekst i ograniczenia, następne kroki, dane krytyczne ([codex compact/prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md)). OpenHands ma sekcje USER_CONTEXT, TASK_TRACKING („PRESERVE TASK IDs”), COMPLETED, PENDING, CODE_STATE, TESTS i inne ([OpenHands summarizing prompt](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/prompts/summarizing_system.j2)). Factory ma cztery sekcje. Nietypowe części A2 (Zaobserwowane wobec Niesprawdzone, Ślepe uliczki, warunek ukończenia) pochodzą wyłącznie z paperu NVIDIA ([arXiv 2611.05306](https://arxiv.org/abs/2611.05306)). Nikt nie opublikował ich ablacji, więc ich osobny wkład zmierzy dopiero K4. Same podstawy są dobrze zmierzone. Według ewaluacji Factory sekcyjne streszczenia aktualizowane przyrostowo wypadają lepiej niż regenerowane (3,70 wobec 3,44 dla Anthropic i 3,35 dla OpenAI), choć tę ewaluację zaprojektowała i przeprowadziła sama Factory ([Factory](https://factory.com/news/evaluating-compression)). Kompakcja nie szkodzi skuteczności: OpenHands 54% wobec 53% przy do 2× niższym koszcie na turę ([OpenHands](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)), a proste maskowanie obserwacji dorównuje streszczaniu LLM-em przy połowie kosztu ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433)).

Spec ma jednak błąd mechaniczny. Sufit ~8K tokenów „przycinany od końca” da się wymusić tylko w briefie `night`, który składa nasz kod. W sesji interaktywnej streszczenie pisze Claude Code. Mamy tylko instrukcje przez `PreCompact` (stdout ≤10 000 znaków; dłuższy Claude Code ucina i dokleja znacznik) i podgląd po fakcie. Spec pomija hook **`PostCompact`**, który dostaje `compact_summary`, „the conversation summary generated by the compact operation”, ale nie może zmienić wyniku ([Hooks reference](https://code.claude.com/docs/en/hooks)). To wystarcza do lintu każdej prawdziwej kompakcji. Hook zapisuje do `.house/compactions.jsonl` długość, obecność ośmiu sekcji i liczbę wpisów „Zaobserwowane” bez źródła, bez treści. Spec myli się też w innym miejscu: sekcja „# Compact instructions” w `CLAUDE.md` **jest** udokumentowana, na stronie kosztów ([Manage costs](https://code.claude.com/docs/en/costs)). Nie wiadomo, jak łączy się ze stdout `PreCompact`, więc dopóki próba tego nie pokaże, należy zostać przy hooku i nie wpisywać obu. Istniał też błąd, w którym `PreCompact` nie odpalał się przy automatycznej kompakcji (v2.1.105–v2.1.114, zamknięty) ([issue mirror](https://claudeissues.com/issue/50467-precompact-hook-never-fires-on-auto-compaction-v2-1-105-v2-1-114-refs-13572)). Akceptacja A2 powinna sprawdzać to na zainstalowanej wersji.

Najmocniejsze nowe dowody dotyczą ustaleń człowieka. „Governance Decay” (czerwiec 2026, 1 323 epizody, siedem rodzin modeli) mierzy naruszenia polityki: **0% przy polityce w pełnym kontekście, 30% po kompakcji**, do 59% dla niektórych modeli. Przypięcie ograniczeń poza kompakcją przywraca 0% ([arXiv 2606.22528](https://arxiv.org/abs/2606.22528)). „The Compaction Cliff” (sierpień 2026) zmierzył, że prompt `/compact` Claude Code na Sonnet 4.6 zachowuje **53% reguł bezpieczeństwa po jednej rundzie i 10% po pięciu**, a typowane zachowanie (TypeCompact) trzyma 96% przez pięć rund ([arXiv 2608.22752](https://arxiv.org/abs/2608.22752)). Codex z tego samego powodu przenosi do 20 000 tokenów wiadomości użytkownika dosłownie, zamiast ufać streszczeniu ([compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)). Hook `SessionStart(compact)` z A2 to więc właściwy mechanizm, ale przywracanie „5 ostatnich tytułów D-###” jest za słabe. Powinien wracać **pełny tekst** obowiązujących ustaleń i odpowiedzi na Q-### w ramach 10 000 znaków, a nadmiar jako ścieżka. Stałe reguły powinny leżeć w głównym `CLAUDE.md`, bo Claude Code wczytuje go z dysku po kompakcji, a reguły z `paths:` „compaction summarizes them away” ([Explore the context window](https://code.claude.com/docs/en/context-window)). Ten sam argument dotyczy sekcji Zrobione. Ślad artefaktów to najsłabszy wymiar **każdego** streszczacza u Factory (≤2,45/5), a zalecenie brzmi: śledzić go osobno, kodem. W `night` A2 już to robi. W sesji interaktywnej powinien to robić `SessionStart(compact)`: lista zmienionych plików z `git diff --stat` ze statusem sprawdzenia z A1.

Pozostałe poprawki są mniejsze. Instrukcja `PreCompact` powinna kazać przenosić sekcje Zaobserwowane, Ślepe uliczki, Ograniczenia i Decyzje z poprzedniego przekazania bez zmian (kompakcja kotwiczona jak u Factory i OpenHands). To bezpośrednia odpowiedź na anty-cel „przypuszczenie, które po dwóch kompakcjach wraca jako fakt”. Każda sekcja powinna być wypełniona albo jawnie oznaczona jako „brak”. Wskaźnik do zapisu powinien podawać `transcript_path`, żeby agent mógł grepować historię jak w Cursorze ([Cursor](https://cursor.com/blog/dynamic-context-discovery)). Cel długości w instrukcji warto ustawić na ~2–3K tokenów, bo tak wyglądają punkty odniesienia Anthropic: streszczenia podagentów 1–2K tokenów ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)), przykładowy `/compact` 1 725 tokenów ([context window](https://code.claude.com/docs/en/context-window)). Sufit 8K może zostać. Codex powinien dostać ten sam szablon przez `experimental_compact_prompt_file` albo `compact_prompt` ([config_toml.rs](https://github.com/openai/codex/blob/main/codex-rs/config/src/config_toml.rs)).

## K2: automat przy ~967K tłumaczy szczyt 897K z pomiaru

Short-context §4 znalazł sesję z kontekstem 897K i spec traktuje ją jak anomalię. Dokumentacja wyjaśnia ją wprost: modele z natywnym oknem 1M (Sonnet 5+, Fable, Haiku 5.5, Opus 4.7+) kompaktują domyślnie „at about 967K tokens” ([Model configuration](https://code.claude.com/docs/en/model-config)). Obniżenie okna automatu to więc **największa pojedyncza dźwignia** w K2, a kolejność ustawień jest udokumentowana, co zamyka otwarte pytanie z §13 speca. Najwyższy priorytet ma `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. `autoCompactWindow` (100K–1M) działa w każdym pliku ustawień. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` to procent **okna automatu**, nie próg w tokenach, i może go tylko obniżyć ([Environment variables](https://code.claude.com/docs/en/env-vars)). `house adapt` powinien więc wpisywać `autoCompactWindow: 200000` do `settings.local.json`, a zmienną środowiskową zostawić skryptom. Okno da się też ustawić per podagent we frontmatterze ([Subagents](https://code.claude.com/docs/en/sub-agents)).

Spec pomija drugi mechanizm: **kompakcję przy bezczynności**, domyślnie włączoną. Dotyczy sesji interaktywnych z TTL cache 1 h, gdy kontekst osiągnął 200 000 tokenów i minęła około godzina od ostatniego żądania. Próg zmienia `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`, minimum 100 000 ([Settings reference](https://code.claude.com/docs/en/settings-reference)). Odpala `PreCompact` z matcherem `auto`, więc nasze instrukcje działają. To dokładnie „kompakcja na przerwie, póki cache jest ciepły”, której K2 chce. Obniżenie progu do dolnej granicy pasma K2 (~120–150K) daje ją bez żadnego kodu.

Wzór opłacalności w §4 pomija jeden składnik. Wywołanie streszczające samo czyta całą historię: z cache, póki jest ciepły, a po przerwie dłuższej niż TTL „the summarization request reprocesses that history as uncached input” ([Prompt caching](https://code.claude.com/docs/en/prompt-caching)). Koszt jednorazowy rośnie więc o 0,1·L przy ciepłym cache i o 1·L przy zimnym. Na subskrypcji główne tury dostają TTL 1 h bez konfiguracji ([Track cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md)), więc domyślną kolumną dla nas jest w = 2, a nie 1,25. Przeliczenie dla P = 40K i R = 2K:

| L (kontekst przed) | n* w specu (w = 2) | n* poprawione, ciepły cache (w = 2) | n* poprawione, zimny cache (w = 2) |
|---|---|---|---|
| 400K | ~3 | ~4 | ~14 |
| 200K | ~6 | ~7 | ~19 |
| 150K | ~9 | ~10 | ~23 |
| 80K | ~25 | ~27 | ~46 |

Przy ciepłym cache wniosek speca się nie zmienia. **Kompaktowanie dużej, zimnej sesji jest jednak drogie**, a tańszą drogę dokumentacja podaje sama: „When you want a fresh start instead of continuity, `/clear` costs nothing” ([Manage costs](https://code.claude.com/docs/en/costs)). Polityka K2 powinna więc przypominać o `/compact` tylko przy ciepłym cache. Na granicy pracy, gdy następne zadanie jest niezależne (np. po `house merge`), powinna proponować `/clear` i stan z `SessionStart`, jak Amp, który zrezygnował z kompakcji na rzecz przekazania do nowego wątku, bo „It's lossy” ([Amp Handoff](https://ampcode.com/news/handoff)). Dla porzuconej ścieżki `/rewind` cofa do prefiksu, który już jest w cache ([Prompt caching](https://code.claude.com/docs/en/prompt-caching)), pod warunkiem że ślepa uliczka zostanie najpierw zapisana w pliku. Nie znaleziono żadnego opublikowanego badania progów kompakcji minimalizujących łączny koszt przy cache. Model z §4 z danymi K0 jest tak dobry, jak cokolwiek dostępnego. Jeśli anegdoty o wadze odczytów cache w limicie tygodniowym są prawdziwe, kompakcja na subskrypcji zwraca się szybciej, niż pokazuje tabela.

## A3: własny runner tak, ale z oceną stanu, izolacją i uczciwą statystyką

Decyzja o własnym runnerze się broni, ale z innego powodu, niż spec zakłada. `claude plugin eval` istnieje i jest dojrzały: foldery przypadków, sześć typów graderów, domyślnie 3 przebiegi, ramię z pluginem i bez, wynik JSON, kody wyjścia, sufit kosztu ([plugin-evals docs](https://code.claude.com/docs/en/plugin-evals.md)). Nie nadaje się jednak na nasz runner z czterech powodów. Nie ładuje `CLAUDE.md` ani `.claude/` projektu („no project CLAUDE.md, no `.claude/`”). Startuje z pustego katalogu. Nie ma graderów w kodzie („There are no custom-code graders”). Nie uruchamia Codexa. Warto natomiast przejąć jego słownik: `tool_used` z `input_match`/`min`/`max`, `tool_order` z `before`/`after`, `regex` z `not_contains`, `file_exists`, głosowanie 2 z 3 dla sędziego LLM, `partialReason`, który oddziela awarię infrastruktury od porażki zadania. Przypadki da się wtedy później wyeksportować, a okresowy przebieg jednego skilla przez oficjalny runner sprawdzi, czy parser A0 nadal zgadza się z Claude Code.

Najważniejsza luka merytoryczna to brak oceny **stanu końcowego**. Anthropic pisze: „A booking agent's claim of success matters less than whether the reservation exists”. Sztywne sekwencje kroków nazywa „overly brittle” ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). OpenAI sprawdza pliki na dysku i `git status --porcelain` po przebiegu ([Testing Agent Skills](https://developers.openai.com/blog/eval-skills)). A3 ma tylko `expect`/`forbid` po wywołaniach. Powinien dostać pole `outcome` z predykatami w stdlib: gałąź i commit scalenia, pliki utworzone lub nietknięte (`.house/checks/`), status zadania w `.house`. To nasza główna przewaga nad plugin eval. Semantykę `expect` trzeba nazwać wprost jako superset, jak tryb `superset` w agentevals ([LangChain evals](https://docs.langchain.com/oss/python/langchain/test/evals)), z licznikami `min`/`max` (np. `house merge` dokładnie raz) i opcjonalnym porządkiem. Porządek trzeba liczyć po pierwszym wystąpieniu w zapisie, bo przy równoległych wywołaniach asercje zależne od pozycji w tablicy bywały niestabilne ([promptfoo](https://www.promptfoo.dev/docs/guides/test-agent-skills/)).

Izolacja to warunek bezpieczeństwa, nie wygoda. Anthropic opisuje przypadek, w którym Claude zyskał nieuczciwą przewagę, czytając **historię git zostawioną przez wcześniejsze próby** ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Sandbox Claude Code na Linuksie (bubblewrap) domyślnie pozwala czytać prawie całą maszynę, „including `~/.ssh` and `~/.aws/credentials` unless restricted” ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Przebieg evalu potrzebuje więc świeżego repo git i `origin` jako lokalnego bare repo. Potrzebuje też `--settings` z `sandbox.failIfUnavailable: true`, pustym `allowedDomains` i `denyRead` dla katalogu domowego, `permissions.deny` dla `git push` oraz flagi `HOUSE_EVAL=1`, która zamienia powiadomienia Signal na zapis w logu. Przed planem A3 trzeba lokalnie sprawdzić trzy rzeczy: czy `claude -p` z tymczasowym `HOME`/`CLAUDE_CONFIG_DIR` zachowuje logowanie subskrypcyjne, czy bubblewrap jest na maszynie nocnej i czy pola `command_execution`/`exit_code` w `codex exec --json` są stabilne.

Statystyka wymaga uczciwego opisu w specu. pass^k (wszystkie k prób udane, wprowadzone w [τ-bench](https://arxiv.org/abs/2406.12045)) to właściwa bramka dla zachowań „zawsze”. Przy n = 3 jest jednak zgrubna. Zachowanie skuteczne w 90% przechodzi 3/3 tylko w **73%** przebiegów, a wynik 3/3 nie wyklucza prawdziwej skuteczności rzędu **37%** (jednostronna granica 95%, rachunek dwumianowy w [notatce](../research_notes/Research%20speców%20Agno%20i%20kontekstu/agent_evals.md)). Anthropic rozdziela więc ewaluacje regresji (blisko 100%, bramka) od ewaluacji zdolności (start nisko, nigdy nie blokują) i „promuje” nasycone zadania do regresji ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Przy małym n przedziały z CLT są za wąskie, więc lepszy jest przedział Wilsona ([Bowyer i in.](https://arxiv.org/abs/2503.01747)). Dwa commity porównuje się parami, przypadek po przypadku ([Miller](https://arxiv.org/abs/2411.00640)). Przy stałym budżecie więcej różnych przypadków daje więcej niż więcej powtórzeń. Anthropic zaleca na start 20–50 zadań z prawdziwych porażek, z wzorcowym rozwiązaniem i z przypadkami negatywnymi, żeby agent nie był optymalizowany jednostronnie. Wiersz wyniku powinien rozróżniać `pass`, `fail`, `paused` i `infra_error` (limit subskrypcji, timeout, autoryzacja, brak sandboxa), a `infra_error` nie wchodzi do k/n. Do tego wersja CLI i `case_hash`, żeby wyniki starej wersji przypadku nie mieszały się z nową.

Sędzia LLM (`criteria`) powinien być rzadki, bo prawie wszystkie zachowania z akceptacji A3 są deterministyczne. Gdy już jest, to w wariancie zalecanym przez Husaina i Anthropic: binarny werdykt z krytyką i wyjściem „unknown”, jedno kryterium na wywołanie, większość z 3 głosów. Werdykt nie blokuje, dopóki kryterium nie zostanie sprawdzone na ręcznie oznaczonych zapisach z raportem TPR/TNR, bo „Agreement can be misleading when failures are rare” ([Husain](https://hamel.dev/blog/posts/llm-judge/)). W `/house-improve` brakuje najważniejszego zabezpieczenia przed anty-celem speca: **zbioru wstrzymanego**. skill-creator dzieli przypadki 60/40 i wybiera wersję „by test score rather than train score to avoid overfitting” ([skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)). Część przypadków `/house-improve` nie może więc czytać w krokach 2–4, a kandydat jest wybierany po wyniku na nich. Krok weryfikacji powinien porównywać parami nową wersję ze snapshotem starej. Sonda po kompakcji (pytania o pliki, ostatni błąd, obowiązujące ograniczenia i ślepe uliczki, jak u Factory) da się oceniać dopasowaniem do faktów z A0/A1, bez sędziego. To naturalny przypadek A3 dla K4.

## A4 i K3: Claude Code rozwiązał połowę problemu offloadu

Opis problemu w A4 („Claude Code przycina długi wynik Bash i środek ginie”) jest nieaktualny. Wynik **udanej** komendy powyżej ~30 000 znaków Claude Code zapisuje w całości do pliku sesji i pokazuje „the path of a file saved to the session directory … plus a preview of up to the first 2,000 characters”. Wynik komendy **z błędem** powyżej ~10 000 znaków dostaje natomiast „a head-and-tail excerpt … with no file path”. Za błąd uchodzi każdy kod 1 poza `grep`, `diff`, `test` i kilkoma innymi ([Tools reference](https://code.claude.com/docs/en/tools-reference)). Czerwone testy i wywrotka treningu, czyli najważniejsze przypadki, nadal tracą środek. Codex i mini-swe-agent też tylko tną głowę i ogon bez pliku ([mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/config/default.yaml), [codex PR #6476](https://github.com/openai/codex/pull/6476)). A4 jest więc nadal potrzebne, ale z innego powodu: pełny wynik komend z błędem, ogon w kopercie (podgląd Claude Code pokazuje tylko początek, a błędy i końcowe metryki są na końcu), miejsce wspólne dla podagentów i Codexa oraz sprzątanie, którego Claude Code nie robi ([issue 31914](https://claudeissues.com/issue/31914-no-automatic-cleanup-of-persisted-tool-result-cache-files-in-claude-projects-too)).

Koperta „~40 linii z każdej strony” nie ma limitu znaków. Linie z paskami postępu tqdm (`\r`) albo zminifikowanym JSON-em mają setki KB, a Claude Code ma udokumentowany problem z plikami o długich liniach ([issue 41092](https://claudeissues.com/issue/41092-persisted-output-files-with-long-lines-cant-be-chunked-by-read-offset-limit)). Agno ogranicza podgląd do 1 200 znaków, przycina linie w wyszukiwaniu do 500 znaków, a stronicowanie dzieli zbyt długą linię zamiast ją gubić ([Agno offload/store.py](https://github.com/agno-agi/agno/blob/main/libs/agno/agno/offload/store.py)). Druga rzecz zmienia sposób myślenia o kopercie. Logi z produkcyjnego middleware MCP (klienci Claude Code, Cursor, Codex, Aider) pokazały **zero** próśb o drugą stronę wyniku ([Vaughan o arXiv 2608.26130](https://codex.danielvaughan.com/2026/08/30/agents-dont-paginate-first-chunk-selection-tool-responses-codex-cli/), źródło wtórne). Koperta musi więc zawierać wszystko, co rozstrzyga sprawę: kod wyjścia, rozmiar, liczbę linii, czas, ogon i gotowe `house out show <id> --grep …`.

K3 opiera się na najmocniejszych dowodach z całego zakresu. Paper NVIDIA zmierzył przy wybiórczym czytaniu z plików od −0,4 do **+40 pp** dokładności, przy oknie odczytu 6–8K znaków ([arXiv 2611.05306](https://arxiv.org/abs/2611.05306)). Próg „~40 KB → najpierw grep” jest bardziej restrykcyjny niż harness (Read odmawia całego pliku dopiero powyżej 256 KB) i tak ma być. Spec nie uwzględnia jednak nowego parametru Read: od v2.1.296 `allow_large: true` czyta cały plik dopasowany do wolnego kontekstu ([Tools reference](https://code.claude.com/docs/en/tools-reference)), co unieważnia K3. Reguła i eval muszą go zakazać dla `.house/sources/*`. Warto też podać rozmiar jednego odczytu (~200 linii albo 8–16K znaków, jak `view` w memory tool i Agno). `house sources` powinien wypisywać spis nagłówków z numerami linii, odpowiednik `doc-stats` z paperu, żeby agent skakał do zakresu zamiast zgadywać słowa do grepa.

## A5–A7: decyzje, pamięć i rutyny potrzebują deterministycznych bezpieczników

W A5 sprawdzenie na prawdziwym pliku znalazło błąd, zanim powstał kod. `contests/grok-bot-wro-2026/.house/DECISIONS.md` ma w nagłówku szablonu (linia 9) wiersz `- **Kto:** człowiek | judge | coordinator`, który naiwny parser odczyta jako wpis. Pola trzeba czytać tylko wewnątrz bloków `## D-###` ([notatka](../research_notes/Research%20speców%20Agno%20i%20kontekstu/offload_memory_routines.md)). Druga luka jest poważniejsza. [`core/protocols/decisions.md`](../../../core/protocols/decisions.md) mówi, że odwrócona decyzja to nowy wpis z odwołaniem do starej, ale nie ma pola, które kod może odczytać. Bez niego `house decisions --by human` pokaże odwróconą decyzję jako obowiązującą, czyli „stale docs are poison delivered continuously” ([Tian Pan](https://tianpan.co/blog/2026-07-02-the-adr-your-agent-never-read), źródło wtórne). MADR rozwiązuje to statusem „superseded by” ([MADR 4.0](https://adr.github.io/madr/)), więc wystarczy opcjonalne pole `Zastępuje: D-###`. Agno wstrzykuje ostatnie decyzje do promptu w bloku `<decision_log>` i trzyma pola `alternatives` i `outcome` ([Agno Decision Log](https://docs.agno.com/learning/stores/decision-log)). Format jednej linii na wpis i opcjonalne pole `Wynik` z retro to ich tani odpowiednik. Nie ma danych ilościowych o tym, czy agenci czytają dzienniki decyzji. Cała wiedza o formacie wstrzykiwania jest anegdotyczna.

A6 robi dobrze, że tylko raportuje. Agno `curate.py` usuwa sam ([curate.py](https://github.com/agno-agi/agno/blob/main/libs/agno/agno/learn/curate.py)). Mem0 według przeglądu kodu wycofał z `add()` decyzje LLM-a o UPDATE/DELETE ([przegląd Mem0](https://zby.github.io/commonplace/agent-memory-systems/reviews/mem0/), źródło wtórne). Jest też opisany przypadek, w którym automatyczne rozwiązywanie konfliktów usunęło potrzebną pamięć ([dev.to](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m), źródło wtórne). Spec nie zna jednak limitu, który Claude Code egzekwuje: przy starcie sesji wczytuje się tylko „first 200 lines of `MEMORY.md`, or the first 25KB”, więc wpisy dalej są niewidoczne ([Memory docs](https://code.claude.com/docs/en/memory)). Ta sama strona opisuje `/doctor prompt-audit`, który raportuje „references to files or commands that don't exist”, ale domyślnie dla `CLAUDE.md`, skilli i reguł, a nie dla auto memory. `house memory lint` pokrywa więc lukę, a nie dubluje narzędzia. Lokalnie 18 z 24 katalogów `projects/` ma `memory/`, w tym projekty służbowe. Raport musi więc podawać tylko ścieżki, numery linii i hashe, a domyślnie obejmować tylko `house` i konkursy. Frontmatter (`metadata.type`, `metadata.modified`) pozwala bez modelu oznaczyć stare wpisy typu `project`, które starzeją się najszybciej.

A7 ma gotowy wzorzec w repo, ale też pułapkę. [`houselib/setup.py`](../../../houselib/setup.py) ustawia dla `house-signal-pull` `OnUnitActiveSec=` razem z `Persistent=true`, a strona man mówi: „this setting only has an effect on timers configured with `OnCalendar=`” ([systemd.timer(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)). Dla odpytywania co kilka minut to nieszkodliwe, ale dla rutyny tygodniowej taka kopia oznacza zgubione przebiegi. Semantykę zaległych przebiegów warto wziąć z zadań lokalnych Claude Desktop. Po wybudzeniu sprawdza się ostatnie siedem dni i „starts exactly one catch-up run for the most recently missed time and discards anything older”, a pominięcia zapisuje się z powodem ([Desktop scheduled tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)). Agno odmawia nowego startu komunikatem „The previous Task run is still active”, a jego zasada „The review queue is the brake” oznacza, że nieprzeczytany raport blokuje następny ([Agno routines.py](https://github.com/agno-agi/agno/blob/main/libs/agno/agno/company/routines.py)). Infrastruktura agenta Signal (jednostka `systemd-run --user` z `RuntimeMaxSec` i `MemoryMax`, blokada bez czekania, audyt jsonl) daje resztę ([projekt agenta Signal](../2026-11-16-signal-claude-agent.md)). Chmurowe scheduled tasks Claude Code odpadają dla pierwszej rutyny. Działają na świeżym klonie bez lokalnych plików i evali, domyślnie pushują gałęzie `claude/` i zużywają subskrypcję „the same way interactive sessions do” ([Routines](https://code.claude.com/docs/en/routines)). Większość rutyny tygodniowej (wersje, `git ls-remote`, wynik smoke) da się zrobić w Pythonie, a `claude -p` z narzędziami tylko do odczytu powinien jedynie streszczać changelogi.

## Wnioski

Z całego researchu wychodzi jeden wzorzec. Rzeczy, które model gubi albo zmyśla, to ślad zmienionych plików, ustalenia człowieka, status sprawdzenia, twierdzenie „testy przechodzą” i stan po evalu. Wszystkie da się policzyć kodem z zapisu, gita albo `.house/`, i za każdym razem tam, gdzie ktoś to zmierzył, wersja liczona kodem wygrywa: detektory z AUROC 0,83–0,95 wobec sędziów ≤0,65, przypięte ograniczenia z 0% naruszeń wobec 30%, osobny indeks artefaktów u Factory. Specy stosują tę zasadę w `night`, ale nie w sesji interaktywnej coordinatora, gdzie ryzyko jest największe, bo tam kompakcje się kumulują. Najwięcej jakości za najmniej kodu dają więc hooki `SessionStart(compact)` i `PostCompact`, a nie dopracowywanie tekstu szablonu.

Druga obserwacja dotyczy tempa zmian. Między 16 a 17 listopada okazało się, że Claude Code zapisuje już duże wyniki do pliku, ma `cost-state`, kompakcję przy bezczynności, `allow_large` i domyślny protobuf w OTel, a Codex ma nowe rekordy zużycia. Parser A0 będzie się psuł przy każdej wersji, więc najcenniejszym testem w całym projekcie jest lokalne porównanie Σ `usage` z `cost-state` na nowej wersji CLI. Rozjazd w sesji bez kompakcji oznacza zmianę formatu, zanim zauważy ją K0 albo A1. Trzy rzeczy pozostają nieznane i żaden research ich nie rozstrzygnie: wagi tokenów w limitach subskrypcji, osobny wkład podziału Zaobserwowane/Niesprawdzone i ślepych uliczek oraz to, jak sekcja „Compact instructions” w `CLAUDE.md` łączy się z `PreCompact`. Pierwsze dwie mierzy K4, trzecią rozstrzyga jedna próba.
