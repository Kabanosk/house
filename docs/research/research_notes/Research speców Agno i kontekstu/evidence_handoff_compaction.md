# Evidence of what a coding-agent run did, hand-off briefs, and compaction (state as of 2026-11-17)

Scope: best practice for (1) run evidence computed from the transcript, not from the agent's claims, and (2) hand-off briefs and context compaction in long-running coding agents. These notes are checked against A1/A2 (spec `2026-11-16-agno-adoptions-design.md` §7–8), K1/K2 (spec `2026-11-16-short-context-design.md` §2–8) and the notes on arXiv 2611.05306. Material older than 2026 is marked **[older: date]**.

## Q1. Anthropic guidance: progress files, hand-offs, what to keep and drop, and how Claude Code compaction actually works

### Takeaway
Anthropic's guidance is consistent: keep state in files plus git, verify before marking anything done, and treat compaction as "keep architectural decisions, unresolved bugs, implementation details; drop redundant tool output." The current Claude Code docs (checked 2026-11-17) confirm the mechanisms our spec relies on: PreCompact stdout becomes the summary instructions, and SessionStart with matcher `compact` re-injects context. They also show three things the spec does not account for. A **PostCompact** hook receives the generated summary. **Idle compaction** is on by default. Native-1M models auto-compact only at **~967K**.

### Cited Findings
**Harness / progress files** **[older: Nov 2025]**
- Anthropic's long-running harness has an initializer agent that creates `init.sh`, a `claude-progress.txt` log, and an initial git commit. Later coding sessions read the git log and progress file, pick the highest-priority unfinished feature, and run `init.sh` plus a basic end-to-end check *before* new work, so that existing breakage is caught first. — [Anthropic, Effective harnesses for long-running agents (2025-11-26)](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Each feature in the feature list carries a `passes` field, and agents may change only that field: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON was chosen because the model was less likely to overwrite it than Markdown. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure modes named in the post: declaring victory too early, marking features done prematurely without testing, leaving undocumented or buggy states, and a later agent seeing progress and "declaring the job done." The post's fixes were one feature per session, self-verification with end-to-end (browser) tests before marking passing, and git plus progress notes. It reports **no quantitative results**. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Context engineering** **[older: Sep 2025]**
- Compaction "preserves architectural decisions, unresolved bugs, and implementation details" and discards redundant tool outputs. The agent continues with the summary plus the five most recently accessed files. Tune by "maximizing recall" first, then "improve precision". — [Anthropic, Effective context engineering for AI agents (2025-09-29)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "One of the safest lightest touch forms of compaction is tool result clearing." Structured note-taking (NOTES.md, to-do lists) persists outside the window. Sub-agents return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)". Agents keep lightweight identifiers such as file paths and load the content just in time. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Context editing plus the memory tool gave +39% over baseline on an internal agentic-search eval, and context editing alone gave +29%. In a 100-turn web-search eval, context editing cut token use by 84%. — [Claude blog, Managing context on the Claude Developer Platform (2025-09-29)](https://claude.com/blog/context-management)

**Claude API mechanisms** (current docs)
- Two compaction modes exist: on demand (beta `compact-2026-09-04`) and at a token threshold (`compact_20260112`, which defaults to 150,000 input tokens with a minimum trigger of 50,000). A custom `instructions` string of up to 16,384 characters **replaces** the default prompt entirely. — [Compaction overview](https://platform.claude.com/docs/en/build-with-claude/compaction), [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold), [Compaction on demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)
- The default summarization prompt is generic: "Write down anything that would be helpful, including the state, next steps, learnings etc. You must wrap your summary in a <summary></summary> block." — [Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)
- `clear_tool_uses_20250919` defaults to trigger 100,000 input tokens and keep 3 tool uses. It has an optional `clear_at_least` "to determine whether context clearing is worth breaking your prompt cache", plus `exclude_tools`. Combined with the memory tool, Claude gets a warning before the clearing threshold so it can save what matters. — [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)

**Claude Code mechanisms** (current docs, read 2026-11-17)
- PreCompact: "When a PreCompact hook exits 0 and doesn't block, Claude Code uses its stdout as instructions for the compaction summary. Keep that stdout under 10,000 characters per hook. Claude Code cuts longer output at the cap and appends a marker." Input includes `trigger` (manual/auto) and `custom_instructions` (the `/compact` argument, or null). It can block with exit 2 or `"decision":"block"`. The `auto` matcher covers both auto-compact and **idle compaction**. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- **PostCompact** receives `compact_summary`, "the conversation summary generated by the compact operation". It has no decision control: it "can't affect the compaction result but can perform follow-up tasks" (for example, logging the summary). — [Hooks reference](https://code.claude.com/docs/en/hooks)
- What survives compaction: project-root CLAUDE.md and unscoped rules are re-injected from disk, and so is auto memory. Claude Code re-reads up to 5 recently modified files, and a file over 5,000 tokens comes back only as a path. Path-scoped rules and nested CLAUDE.md "compaction summarizes them away". "Context that hooks added earlier" is summarized with the rest. SessionStart hooks matching `compact` run and are added to the compacted context. — [Explore the context window](https://code.claude.com/docs/en/context-window)
- In Anthropic's illustrative session, a 22,225-token context compacts to a **1,725-token** conversation summary. — [same](https://code.claude.com/docs/en/context-window)
- The CLAUDE.md "# Compact instructions" section **is** documented, on the costs page ("You can also customize compaction behavior in your CLAUDE.md file"). This contradicts spec A2's statement that a section in CLAUDE.md "nie jest udokumentowanym mechanizmem". — [Manage costs](https://code.claude.com/docs/en/costs)
- Default auto-compact thresholds: models with a native 1M window (Sonnet 5+, Fable, Haiku 5.5, Opus 4.7+) compact "at about 967K tokens by default". Sonnet/Opus 4.6 without extended context compact at 200K. — [Model configuration](https://code.claude.com/docs/en/model-config)
- The window can be set with `autoCompactWindow` (100K–1M, any settings file), `--autocompact`, `/autocompact` (saved per model), `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (highest precedence), or per subagent through `autoCompactWindow` frontmatter. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` is a percentage *of the auto-compact window* and can only lower it. — [Model configuration](https://code.claude.com/docs/en/model-config), [Environment variables](https://code.claude.com/docs/en/env-vars), [Subagents](https://code.claude.com/docs/en/sub-agents)
- **Idle compaction** is on by default. It applies to interactive sessions on the 1h cache TTL when the context has reached 200,000 tokens (adjustable with `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`, minimum 100,000) and about an hour has passed since the last request. Claude Code then shows "Compacted while idle, before the prompt cache expired". — [Settings reference](https://code.claude.com/docs/en/settings-reference)

### Inferences
- Our use of PreCompact and SessionStart(compact) matches the documented mechanism. A CLAUDE.md "Compact instructions" section also exists, and the docs do not say how it combines with PreCompact stdout.
- **Spec A2's ~8K ceiling, "truncated from the end", cannot be enforced in interactive sessions.** Claude Code writes the summary itself. We can only instruct (PreCompact) and observe afterwards (PostCompact `compact_summary`). Truncation from the end works only for briefs that our own code assembles (`night`).
- Anthropic's own reference points (1–2K-token sub-agent summaries, a 1,725-token example summary, and the 7–12K-character SDK summaries Factory measured, see Q2) put a typical good summary at ~2–3K tokens. An 8K-token ceiling is generous, which is fine as a ceiling but should not be what the instructions aim for.
- Idle compaction already approximates "compact at a pause, while the cache is warm". K2 should configure it, not ignore it.

### Gaps
- No Anthropic source gives measured accuracy for its Claude Code compaction prompt, or for progress-file hand-offs versus none.
- The docs do not say whether a CLAUDE.md "Compact instructions" section and PreCompact stdout are concatenated or one wins. This needs a run to find out.
- A May–June 2026 issue reported PreCompact not firing on auto-compaction (v2.1.105–v2.1.114, closed). The fix is not confirmed for the installed version. — [issue mirror](https://claudeissues.com/issue/50467-precompact-hook-never-fires-on-auto-compaction-v2-1-105-v2-1-114-refs-13572)

## Q2. How others implement compaction and hand-off, and with what measured results

### Takeaway
The best-measured results support three things. First, structured, sectioned summaries that are updated incrementally beat freeform regenerated ones (Factory). Second, cheap observation masking matches LLM summarization on SWE-bench (JetBrains/NeurIPS DL4C), and the NVIDIA paper shows early compaction to a hand-off brief costs little accuracy. Third, "artifact trail" (which files changed) is the weakest dimension of *every* summarizer, so it should be tracked by code. Product teams split between automatic compaction (Claude Code, Codex, OpenHands, Cline) and user-initiated hand-off to a fresh thread (Amp), which keeps the full history searchable as a file (Cursor).

### Cited Findings
- **Factory probe eval** **[older: Dec 2025]**. Hundreds of compression points over 36,611 messages from production SWE sessions. Four probe types: recall, artifact, continuation, decision. Six dimensions were graded 0–5 by a GPT-5.2 judge. Overall scores: Factory 3.70, Anthropic 3.44, OpenAI 3.35. Artifact trail was the lowest dimension for all three (2.45 / 2.33 / 2.19). Compression ratios: OpenAI 99.3%, Anthropic 98.7%, Factory 98.6%. — [Factory, Evaluating context compression (2025-12-16)](https://factory.com/news/evaluating-compression)
- Factory's summary has explicit sections (session intent, file modifications, decisions made, next steps), and "each section works as a checklist that the summarizer must fill or explicitly leave empty". It is **anchored iterative**: only the newly truncated span is summarized and merged into the persistent summary, whereas the Anthropic SDK regenerates the whole summary each time. Factory's recommendations: optimize tokens *per task*, not per request; handle artifact tracking "separately, through a dedicated artifact index or explicit file-state tracking". OpenAI's compaction drops file paths, and on artifact probes it scored 2.8 against Factory's 3.6. — [same](https://factory.com/news/evaluating-compression)
- Caveat: the evaluation was designed and run by Factory itself. — [same](https://factory.com/news/evaluating-compression)
- **OpenHands** **[older: Apr 2025]**. On a SWE-bench Verified subset (size not stated), the condenser solved 54% against 53% for the baseline, with "up to 2x" lower per-turn API cost. After condensation, cost settles below half the baseline. Condensing occasionally costs an extra turn. — [OpenHands blog (2025-04-09)](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)
- OpenHands SDK source: `LLMSummarizingCondenser` defaults are `max_size=240` events and `keep_first=2`. The summary prompt is a "state summary" over events *including previous summaries* (incremental), with sections USER_CONTEXT, TASK_TRACKING ("PRESERVE TASK IDs"), COMPLETED, PENDING, CURRENT_STATE, CODE_STATE, TESTS, CHANGES, DEPS and VERSION_CONTROL_STATUS. It has no observation/hypothesis split and no dead-ends section. — [OpenHands software-agent-sdk, llm_summarizing_condenser.py](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py), [summarizing_system.j2](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/prompts/summarizing_system.j2)
- **"The Complexity Trap"** (Lindenbauer et al., JetBrains, NeurIPS'25 DL4C) **[older: Aug–Oct 2025]**. Simple observation masking "halves cost relative to the raw agent" while matching, and sometimes slightly exceeding, LLM summarization's solve rate. A hybrid cuts cost a further 7% relative to masking and 11% relative to summarization. — [arXiv 2508.21433](https://arxiv.org/abs/2508.21433). The search summary of the PDF gave masking 54.8% against 53.8% raw; I verified only the abstract. — [PDF v2](https://arxiv.org/pdf/2508.21433v2)
- **NVIDIA, "You don't need long context"** (2026-11-03). End-of-conversation compaction to a hand-off recap at 16K–48K limits changed accuracy by −3.7 to +5.6 pp. The recap prompt asks to "Separate observations from unverified ideas", with Dead ends and "the condition for completion". See the local notes, `docs/research/2611.05306-you-dont-need-long-context.md`. — [arXiv 2611.05306](https://arxiv.org/abs/2611.05306)
- **ACON** (Microsoft/KAIST, ICML 2026). Compression *guidelines* are optimized in natural language: pairs where full context succeeds and compressed context fails are analysed by an LLM, and the guideline is updated. Peak tokens fell 26–54% while task success rose on AppWorld, OfficeBench and multi-objective QA. — [arXiv 2510.00615](https://arxiv.org/abs/2510.00615v2), [PMLR](https://proceedings.mlr.press/v306/kang26b.html)
- **Codex CLI** (openai/codex source, main branch, last commit 2026-11-17). The local compact prompt reads: "You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task. Include: Current progress and key decisions made; Important context, constraints, or user preferences; What remains to be done (clear next steps); Any critical data, examples, or references needed to continue". The next model sees the prefix "Another language model started to solve this problem and produced a summary...". Up to `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000` tokens of the user's own messages are carried verbatim. Config keys: `compact_prompt`, `experimental_compact_prompt_file`, `model_auto_compact_token_limit` (and `_scope`). — [codex compact/prompt.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/prompt.md), [summary_prefix.md](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/compact/summary_prefix.md), [compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs), [config_toml.rs](https://github.com/openai/codex/blob/main/codex-rs/config/src/config_toml.rs)
- Remote compaction (`/responses/compact`, an encrypted opaque item) and a "session memory compact" tier are described only by a third-party blog that does not cite the source code; treat these as unverified. The same blog wrongly says Claude Code does not re-read files after compaction, which contradicts Anthropic's docs. — [danielvaughan.com deep dive (2026-04-14)](https://codex.danielvaughan.com/2026/04/14/context-compaction-deep-dive-codex-cli-claude-code-opencode/)
- **Amp** **[older: Oct 2025]** removed compaction. Its reasons: "It's lossy", and it "encourages long, meandering threads". The replacement is **Handoff**: the user states the goal of the next thread, Amp "analyzes the current thread" and produces a draft starting prompt plus a list of relevant files, and the user edits the draft before sending. No metrics were published. — [Amp, Handoff (No More Compaction) (2025-10-23)](https://ampcode.com/news/handoff)
- **Cursor** (Jan 2026): "we use the chat history as files to improve the quality of summarization. After the context window limit is reached... we give the agent a reference to the history file." Long tool outputs and terminal sessions are also written to files. Internal A/B: 46.9% fewer tokens on runs with MCP tools. — [Cursor, Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)
- **Cline** auto-compact summarizes as the conversation "approaches the model's context window limit", keeping "all technical details, code changes, and decisions". The summary "leverages your existing prompt cache" and so "costs about the same as any other tool call". "Structured task lists can help maintain progress across summarizations". No metrics published. — [Cline docs, Auto Compact](https://docs.cline.bot/features/auto-compact)

### Inferences
- Our 8-section template is a superset of Codex's 4 bullets, OpenHands' sections and Factory's 4 sections. Its unusual parts (Observed vs Unverified, Dead ends, completion condition) come only from the NVIDIA paper. No product we found has published an ablation of those parts (see Q3).
- Factory's artifact finding directly supports A2's choice to have code fill "Zrobione" for `night`. For interactive sessions no code fills it today.
- Anchored, incremental summarization (Factory, OpenHands) is the main structural difference from how Claude Code works: it regenerates the summary from a history that already contains the previous summary. That matters for the anti-goal "hypothesis returns as fact after two compactions".
- The pattern shared by Amp, Cursor and Anthropic's harness is to keep the full history on disk and make the brief an index. A2's "pointer to the full record" is in line with best practice.

### Gaps
- No published Cursor or Devin compaction prompt or eval was found. Devin's session hand-off was not researched (no primary source surfaced).
- Roo Code's `new_task` / condense thresholds were not verified (Cline's docs do not cover `new_task`).
- The JetBrains paper's finding that summarization makes trajectories longer is known only from secondary memory and was not verified.

## Q3. Separating observations from hypotheses, dead-end tracking, completion conditions and constraint retention: who does it, and is there evidence it helps

### Takeaway
Direct ablations of "observed vs unverified" or "dead ends" sections were **not found**; the support comes from the NVIDIA paper's qualitative Appendix A plus related findings. The strongest new quantitative evidence is about **human constraints**: summaries lose them, and losing them causes violations. Keeping them out of the lossy summary (pinning, or re-injecting them by code) brings violations back to zero.

### Cited Findings
- "Governance Decay" (June 2026): across 1,323 episodes and seven model families, violations rose from 0% with the policy in full context to **30% after compaction**, reaching 59% for some models. When the constraint survived the summary, violations stayed at 0%; when it was dropped they reached 38%. "Constraint Pinning", which quarantines constraints from compaction, restores 0%. — [arXiv 2606.22528](https://arxiv.org/abs/2606.22528)
- "The Compaction Cliff" (Aug 2026): Claude Code's `/compact` prompt on Sonnet 4.6 preserves **53% of safety rules after one round and 10% after five**, across 20 production agent configurations. A rule needs exact wording to stay enforceable, yet it is summarized at the same rate as an episodic log. Typed retention ("TypeCompact") keeps 96% recall over five rounds. — [arXiv 2608.22752](https://arxiv.org/abs/2608.22752)
- A practitioner paper on months-long LLM-assisted development keeps anti-recurrence stores for **decisions and dead ends**: an extraction pass proposes candidates at session end and an operator triages them. It is not a benchmark. — [arXiv 2609.05510](https://arxiv.org/html/2609.05510v1) (search snippet only)
- The Memex paper keeps structured summaries and indices in context and the full evidence outside it, and explicitly tracks which branches are dead ends. — [arXiv 2603.04257](https://arxiv.org/pdf/2603.04257) (search snippet only)
- The NVIDIA recap prompt has "Separate observations from unverified ideas", "Dead ends - failed approaches that should not be repeated" and "the condition for completion". Appendix A argues that compaction should be a forward-looking brief, not a narrative. See the local notes. — [arXiv 2611.05306](https://arxiv.org/abs/2611.05306)
- Anthropic's harness uses an explicit completion criterion per feature (the `passes` field with test steps). — [Anthropic harness post](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Codex carries recent user messages verbatim (up to 20K tokens) instead of trusting the summary to keep user instructions. — [codex compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)
- Claude Code re-injects project-root CLAUDE.md and unscoped rules from disk after compaction, but path-scoped rules are summarized away. "If a rule must persist across compaction, drop the `paths:` frontmatter or move it to the project-root CLAUDE.md." — [Explore the context window](https://code.claude.com/docs/en/context-window)
- Sonnet 5 system card (2026-06-30): during training review, "a clear increase was in fabricating information, especially to make tasks with insufficient information solvable", plus "presenting an answer... that its private reasoning had shown to be wrong or had not actually derived". — [Claude Sonnet 5 System Card](https://www-cdn.anthropic.com/480e0bb54327b9622282e9c39a83a4f490ed377e/Claude%20Sonnet%205%20System%20Card.pdf)

### Inferences
- Human constraints should not depend on the summary. Spec A2's SessionStart re-injection of "the last ~5 D-### titles" is the right mechanism, but titles alone are weaker than verbatim pinned constraints. The evidence supports re-injecting the full text of the constraints still in force.
- Repeated summarization degrades content (53%→10% over five rounds). This supports passing the previous hand-off's Observed, Dead ends and Constraints sections forward unchanged instead of re-summarizing them, and it supports the spec's anti-goal about hypotheses becoming facts.
- Model fabrication of missing inputs is documented for Sonnet 5, so a summary written by the model can also invent "observations". Requiring a source on each Observed entry, and having code check the sources, is justified.

### Gaps
- No ablation measures the separate benefit of an Observed/Unverified split or a dead-ends list for retry success. K4 will have to measure it.

## Q4. Cost interaction with prompt caching, and when compaction pays off

### Takeaway
Compaction invalidates the conversation cache by design. The summarization call itself re-reads the whole history: cheaply from cache while it is warm, at full input price when cold. The spec's break-even formula leaves out this term. Claude Code's idle compaction exists precisely to compact *before* the 1h cache expires. `/rewind` and `/clear` are cheaper alternatives to compaction in specific cases.

### Cited Findings
- "Compaction replaces your message history with a summary. By design, this invalidates the conversation layer." The project-context layer is rebuilt even if unchanged. "To produce the summary, Claude Code sends a separate request... While the cache is warm, that request reads your prefix from the cache... After a break longer than the cache lifetime... the summarization request reprocesses that history as uncached input." — [Prompt caching (Claude Code)](https://code.claude.com/docs/en/prompt-caching)
- "run `/compact` at a natural break in your work, such as between tasks, instead of waiting for auto-compaction to trigger mid-task. If you've gone down a path you want to abandon entirely, `/rewind`... Rewinding truncates back to a prefix that is already cached." — [same](https://code.claude.com/docs/en/prompt-caching)
- "`/compact` reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, `/clear` costs nothing." — [Manage costs](https://code.claude.com/docs/en/costs)
- `/usage` reports "expected rebuilds" (compaction or tool-result clearing) separately from cache misses. — [Manage costs](https://code.claude.com/docs/en/costs)
- In the API, tool-result clearing breaks the cache, and `clear_at_least` exists to make that break "worthwhile". — [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Factory: "Optimize for tokens per task, not tokens per request. Lower compression ratios can pay off if they reduce re-fetching." — [Factory](https://factory.com/news/evaluating-compression)
- The NVIDIA paper's cost savings assume cheaper serving of short contexts. At nominal API prices, GPT on SWE-bench went from $168 to $186–203. See the local notes. — [arXiv 2611.05306](https://arxiv.org/abs/2611.05306)
- Codex issue reports (via secondary source) describe a v0.118 regression in which compaction fired about twice as often and roughly doubled or tripled token use. This is unverified against the issue itself. — [danielvaughan.com](https://codex.danielvaughan.com/2026/04/14/context-compaction-deep-dive-codex-cli-claude-code-opencode/)

### Inferences
- The spec §4 one-time cost `5R + w·(P+R)` should add the summarization read of L: **+0.1·L when the cache is warm, +1·L when it is cold**. Warm, with P=40K, R=2K and w=1.25: at L=150K, n* rises from ~6 to ~7; at L=400K it rises from ~2 to ~3. Cold, at L=400K, the one-time cost is about 460K-equivalent, so n* rises to ~13. The conclusion stays the same while the cache is warm, but **compacting a large, cold session is expensive**. The cheaper option there is `/clear` plus a hand-off from files.
- Idle compaction (1h TTL, ≥200K by default, ~1h idle) already does "compact during a pause, before the cache expires". Lowering `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` to the K2 band (~120K–150K) aligns it with our policy at no extra code.
- The max session of 897K in spec §4 is consistent with the documented ~967K default for native-1M models. Lowering the auto-compact window is the single biggest lever.

### Gaps
- No published empirical study gives compaction thresholds that minimize total cost under prompt caching for Claude Code or Codex. Our §4 model plus K0 data is as good as anything found.
- It is not documented whether subscription limits weight cache reads the same way the API does (already spec question 1).

## Q5. Evidence vs claims: detecting "says tests pass but didn't run them", reward hacking, and presenting run evidence

### Takeaway
False-success claims are common. LLM judges reading the transcript are poor at catching them (AUROC ≤0.65), while simple detectors grounded in the trajectory or environment state do much better. Labs and METR document coding agents that edit tests, hard-code outputs and fabricate. The best-practice response is to (a) re-run the acceptance check independently and fail closed, (b) compute evidence deterministically from the tool trace (which commands ran, their exit status and their order relative to edits), and (c) show reviewers the trace facts, not the agent's narrative.

### Cited Findings
- "From Confident Closing to Silent Failure" (June 2026, FAGEN@ICML2026). False success, where the agent asserts completion but the environment state disagrees, accounts for 45–48% of failures in single-control τ²-bench domains and **75.8%** in AppWorld self-assessing coding-agent trajectories with explicit status claims. Lightweight TF-IDF detectors reach AUROC 0.83 and 0.95. **No configuration of 5 LLM judges × 5 prompt strategies exceeded AUROC 0.65** (0.54 on AppWorld API traces). At the same flag rate the detectors recover 4–8× more false successes. Judges rely on "confident closing language" rather than verified state changes. Recommendation: "Don't use LLM judges as the primary monitor for false success." — [arXiv 2606.09863](https://arxiv.org/abs/2606.09863)
- "Failure as a Process" (July 2026): 3,843 Terminal-Bench trajectories from 7 models and 3 scaffolds (OpenHands, mini-SWE, Terminus2). Failures "typically begin within the first few execution steps" but "often remain hidden until recovery is no longer possible", and are driven mainly by epistemic errors. A search snippet cites fabricated success in 26% of failed trajectories, which I did not find in the abstract (unverified). — [arXiv 2607.09510](https://arxiv.org/abs/2607.09510)
- AgentSWE: 6 of 42 final Creation reports and 3 of 19 Optimization reports claim completions that the trajectory contradicts (search snippet, unverified). — [arXiv 2610.13361](https://arxiv.org/html/2610.13361v1)

### Inferences
- A1's design (deterministic, nothing inferred, transcript as the only source) matches what the evidence favours over LLM judges. Two gaps remain: A1 does not compare the agent's **claim** with the trace, and it does not check **order** (whether the check ran after the last edit).
- `house check` as an independent gate is the "clean re-run, fail closed" defence. A1 evidence explains *why* a run failed but must never replace the gate.
- Edits to test files or the acceptance harness are the most-documented coding hack. A1 already counts guard refusals. Listing *successful* edits to test-like paths is a cheap addition.

### Gaps
- No published system was found that diffs "claimed checks" against "executed checks" in a coding-agent report. The idea is an extrapolation from 2606.09863.
- METR's 2026 reports (MirrorCode, Frontier Risk) could not be opened. Their claims about agents peeking at tests are secondary only.

## Q6. How to evaluate whether a hand-off format works

### Takeaway
There are two measured methods. Probe-based QA after compaction (Factory: recall, artifact, continuation and decision probes, graded per dimension) checks what survived. Downstream task success and cost, paired full-vs-compressed (NVIDIA, ACON, OpenHands), checks whether what survived was enough. ACON adds a loop: failures where full context succeeds but compressed context fails are used to rewrite the compaction guideline. Because of the false-success findings, graders should be grounded in transcript or state facts where possible, not only in an LLM judge.

### Cited Findings
- Factory probes: "Which files have we modified?" and "What was the original error message?" are examples. After compression the agent answers. Six dimensions (accuracy, context awareness, artifact trail, completeness, continuity, instruction following) are scored 0–5 by an LLM judge. — [Factory](https://factory.com/news/evaluating-compression), [Factory docs guide](https://docs.factory.ai/guides/power-user/evaluating-context-compression)
- ACON's paired-trajectory guideline optimization: peak tokens −26–54% with better success. — [arXiv 2510.00615](https://arxiv.org/abs/2510.00615v2)
- NVIDIA measures task accuracy and cost under FHA/EoCC/SAC on SWE-bench and Terminal-Bench. See the local notes. — [arXiv 2611.05306](https://arxiv.org/abs/2611.05306)
- Constraint-retention probes measure rule recall after N compaction rounds (Compaction Cliff), and violation rate after compaction (Governance Decay). — [arXiv 2608.22752](https://arxiv.org/abs/2608.22752), [arXiv 2606.22528](https://arxiv.org/abs/2606.22528)
- LLM judges are weak at verifying state claims (AUROC ≤0.65). — [arXiv 2606.09863](https://arxiv.org/abs/2606.09863)
- A paper on agentic context management argues each compaction should be verified for information loss. — [arXiv 2607.21503](https://arxiv.org/html/2607.21503v1) (search snippet)

### Inferences
- For `house`, most probe answers have ground truth that A0/A1 can compute: files changed (git), last error text, whether `house check` ran, open Q-###, active D-###. Probes can therefore be graded by string or set match rather than an LLM judge, which is cheap and stdlib-only.
- PostCompact's `compact_summary` makes a structural lint possible on every real compaction (8 sections present, Observed entries carry sources, length). This is a lint, not a quality grade.
- Retry-level metrics that A1 can compute: (a) success of attempt N≥2, (b) **dead-end repeat rate**, meaning attempt N runs a failing command or approach that an earlier attempt recorded as a dead end, (c) tokens to first `house check`.

### Gaps
- No public probe set exists for coding hand-offs (Factory published examples only). We will need to write our own.
